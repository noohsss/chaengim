# 챙김 MVP — 제품 요구사항 및 기술 설계

## 1. 제품 정의

챙김은 청년이 정부·지자체 정책을 발견한 뒤 저장하고, 신청 상태·우선순위·메모를 관리하며, AI로 다음 행동을 판단할 수 있는 반응형 웹 서비스다.

핵심 검증 목표는 **정책을 챙긴 사용자가 다시 방문해 상태를 관리하는가**이다. 별도 행동 분석 기능은 넣지 않고 직접 사용과 피드백으로 검증한다.

핵심 흐름:

```text
정책 탐색 → 챙기기 → 상태·우선순위·메모 관리
→ AI 분석 또는 2~3개 정책 비교
→ 공식 신청처 이동 → 신청 결과 기록
```

## 2. 제품 요구사항

### 사용자와 인증

- 핵심 사용자는 청년이며 범정부 혜택 중 청년 관련 정책도 함께 제공한다.
- 비회원도 정책 검색과 상세 조회가 가능하다.
- 로그인은 Supabase Auth의 Google OAuth만 제공한다. 처음 챙길 때 Google 로그인을 요청하고, 인증 후 원래 정책으로 복귀한다.
- 마감 알림 주소는 Google 계정에서 제공된 이메일을 우선 사용한다. 이메일이 제공되지 않으면 설정에서 알림용 이메일을 별도로 입력하고 인증하게 한다.
- 프로필은 출생연도, 시·도, 시·군·구, 취업·재학 상태를 선택 입력한다.
- 탈퇴 시 프로필, 챙김, 메모, 알림, 신청 결과, AI 결과와 인증 계정을 즉시 영구 삭제한다.

### 정책 탐색

- 홈은 서비스 가치와 이용 흐름을 소개한 뒤 실제 정책 검색으로 바로 이어지는 소개·탐색 결합형 랜딩 페이지로 제공한다.
- 키워드, 카테고리, 시·도, 시·군·구 필터를 제공한다.
- 사용자 공통 카테고리는 `일자리·창업`, `주거`, `교육`, `금융`, `복지·문화`, `참여·권리`, `기타`로 통일한다.
- 검색어가 없으면 신청 가능한 정책을 마감 임박순으로, 검색어가 있으면 관련도 우선으로 정렬한다.
- 상세 화면에는 지원 내용, 대상, 신청 조건, 기간, 신청 방법, 담당기관, 문의처, 공식 신청 링크, 원본 출처와 최근 갱신 시각을 표시한다.
- 마감되거나 외부 API에서 사라진 정책은 신규 탐색에서 제외하되 기존 사용자의 챙김 기록에서는 보존한다.

### 내 챙김

- 챙기기·삭제, 자유 메모, `높음·보통·낮음` 우선순위를 지원하며 기본값은 `보통`이다.
- 신청 상태는 `관심 → 확인 중 → 신청 예정 → 신청 완료 → 결과 기록`의 5단계다.
- 결과 기록에는 `선정·탈락·대기·취소`, 결과일, 결과 메모를 저장한다.
- 상태·우선순위·마감일·최근 수정일로 필터와 정렬을 제공한다.
- 공식 신청 버튼은 외부 기관 페이지를 새 탭으로 열며 서비스 내부 신청이나 신청 대행은 하지 않는다.

### AI 분석 및 비교

- 사용자가 요청할 때만 서버에서 Gemini API를 호출한다.
- 기본 모델은 안정 버전 `gemini-3.5-flash-lite`로 고정하고 `@google/genai`와 Zod 기반 구조화 출력을 사용한다. [Gemini 모델 안내](https://ai.google.dev/gemini-api/docs/models), [구조화 출력 안내](https://ai.google.dev/gemini-api/docs/structured-output)
- 내 챙김 분석은 저장 정책이 1개 이상일 때 실행하며 다음을 반환한다.
  - 먼저 확인할 정책과 이유
  - 마감 임박 정책
  - 추가 확인이 필요한 조건
  - 현재 상태·우선순위 요약
- 정책 비교는 내 챙김에서 정확히 2~3개를 선택해 실행하며 지원 내용, 조건, 기간, 주요 차이, 먼저 확인할 정책과 이유를 반환한다.
- 입력은 정책의 정규화 데이터와 출처 원문, 사용자 상태·우선순위·메모, 최소 프로필로 제한한다.
- 자격이나 수급 가능성을 확정하지 않으며, 원문에 없는 판단은 추론 또는 확인 필요 사항으로 표시한다.
- 사용자 메모와 외부 원문은 명령이 아닌 분석 대상 데이터로 취급한다.
- 결과 항목마다 근거 정책을 연결하고 생성 시각, 모델명, 정책 버전을 표시한다.
- 분석과 비교별 최근 결과를 저장한다. 입력 정책이나 사용자 기록이 변경되면 이전 결과를 오래된 결과로 표시하고 재분석을 안내한다.
- Gemini 오류·스키마 검증 실패 시 결과를 저장하지 않고 재시도 가능한 오류 화면을 제공한다.

### 알림

- 헤더 알림함에 읽지 않은 개수를 표시하고 개별·전체 읽음 처리를 지원한다.
- 내 챙김 카드와 목록에 마감 임박 배지를 표시한다.
- 마감 7일 전과 1일 전에 웹 알림과 Resend 이메일을 생성한다.
- 마감일이 없거나 상시 모집인 정책에는 마감 이메일을 발송하지 않는다.
- 저장 정책의 마감일, 주요 신청 조건, 공식 신청 링크가 변경되면 웹 알림을 생성한다.
- 이메일은 전체 수신 여부를 설정할 수 있으며 기본 수신 상태는 가입 과정에서 명시적으로 선택한다.
- 동일 사용자·정책·알림 종류·기준일 조합은 한 번만 발송한다.
- 예약 작업은 한국 시간 오전 9시를 기준으로 매일 실행한다.

## 3. 기술 설계

### 애플리케이션 구조

- Next.js App Router, TypeScript, Tailwind CSS, shadcn/ui를 사용한다.
- 모바일과 데스크톱을 동일 비중으로 지원한다. 모바일은 카드와 단계형 선택, 데스크톱은 다단 목록과 비교 패널을 사용한다.
- Supabase는 PostgreSQL, Auth, Row Level Security를 담당한다.
- 외부 API, Gemini, Resend 키는 서버 전용 환경변수로 관리한다.
- Vercel Cron에서 정책 동기화와 알림 발송 Route Handler를 호출하고 Cron secret으로 보호한다.
- 운영 화면은 만들지 않는다. 동기화 문제는 Vercel 로그와 운영자 이메일로 확인하고 데이터 예외는 Supabase 관리 화면에서 처리한다.

주요 화면:

- `/`: 서비스 소개와 정책 탐색을 결합한 랜딩 홈
- `/policies/[id]`: 정책 상세
- `/my`: 내 챙김 현황·필터·상태 관리
- `/my/compare`: 2~3개 정책 선택 및 비교
- `/my/analysis`: 최근 분석과 재분석
- `/notifications`: 웹 알림함
- `/settings`: 프로필, 이메일 수신, 계정 삭제
- `/auth/callback`: Supabase OAuth·매직링크 콜백

### 공공 API 통합

- 온통청년 API를 화면에서 실시간 호출하지 않고 매일 한 번 내부 DB로 동기화한다.
- 온통청년의 인증키 승인형 API를 단일 정책 출처로 사용한다. [온통청년 API 이용 안내](https://www.youthcenter.go.kr/cmnFooter/openapiIntro/oaiGuide)
- 실제 API 응답 샘플을 fixture로 보존해 필드 변경을 계약 테스트로 감지한다.
- 공통 정책 형식은 제목, 요약, 지원 내용, 조건, 신청 기간, 신청 방법, 기관, 문의처, 신청 URL, 지역 코드, 공통 카테고리, 검색 키워드, 상태를 포함한다.
- 출처별 식별자와 원문 URL은 `policies.source_refs`에 보존하고 원본 payload는 DB에 저장하지 않는다.
- 온통청년 외부 ID가 같은 정책은 기존 대표 정책을 갱신하고, 다른 외부 ID는 별도 정책으로 저장한다.
- 동기화는 출처별 응답을 독립적으로 정규화한 뒤 대표 정책을 upsert하는 방식으로 수행하며, 한 출처의 실패가 다른 출처의 성공 데이터를 제거하지 않게 한다.
- 정책의 핵심 필드가 바뀌면 버전 해시를 갱신하고 저장 사용자의 기존 AI 결과와 알림 판단에 사용한다.
- 검색은 PostgreSQL 전문검색과 trigram 부분 일치를 조합해 제목, 키워드, 기관, 요약을 조회한다.

### 핵심 데이터 모델

Supabase가 관리하는 `auth.users` 외에 애플리케이션 테이블은 다음 5개만 사용한다.

- `profiles`: 사용자 최소 프로필, 알림 이메일과 이메일 수신 여부
- `policies`: 대표 정책, 지역 코드, 출처 참조, 현재 버전과 검색 벡터
- `saved_policies`: 사용자별 상태, 우선순위, 메모와 신청 결과
- `ai_results`: 분석 종류, 대상 정책 ID, 입력 해시, 모델과 구조화 결과
- `notifications`: 웹 알림, 읽음 상태와 이메일 발송 상태

출처별 외부 ID와 원문 URL은 `policies.source_refs`에, 지역은 `policies.region_codes`에 저장한다. 신청 결과는 `saved_policies`에, 이메일 발송 상태는 `notifications`에 함께 저장한다. 외부 API 원본 payload, 별도 동기화 이력과 통합 관계 테이블은 만들지 않고 구조화된 서버·Vercel 로그를 사용한다.

사용자 소유 테이블에는 `auth.uid() = user_id` RLS를 적용한다. 활성 정책은 익명 조회를 허용하고, 비활성·보관 정책은 해당 정책을 챙긴 사용자만 조회할 수 있다. 정책 쓰기와 AI·알림 생성은 서버 역할만 수행한다.

### 서버 인터페이스

- 정책 목록 조회는 검색어, 카테고리, 지역과 페이지 번호를 받고, 상세 조회는 정책 ID를 받는다.
- 챙김 API는 추가·삭제와 상태·우선순위·메모·결과 갱신을 제공한다.
- AI API는 분석 또는 비교 요청을 받아 현재 사용자 소유 정책인지 검증한 뒤 구조화 결과를 반환한다.
- 알림 API는 목록 조회, 개별 읽음, 전체 읽음을 제공한다.
- 계정 삭제 API는 재인증된 사용자만 실행하며 관련 데이터를 트랜잭션으로 삭제한다.
- Cron API는 정책 동기화와 마감 알림 생성을 분리하고 재실행해도 중복 결과가 생기지 않도록 만든다.

## 4. 구현 순서

1. Next.js 프로젝트, UI 토큰, Supabase 클라이언트, 환경변수 검증, 기본 배포 구성을 만든다.
2. Supabase 마이그레이션, RLS, Google OAuth 인증, 프로필과 탈퇴 흐름을 구축한다.
3. 온통청년 API 어댑터, 정규화, 외부 ID 기반 중복 방지, 검색 인덱스와 일일 동기화를 구현한다.
4. 공개 탐색·상세와 로그인 복귀를 포함한 챙기기 흐름을 완성한다.
5. 내 챙김의 상태·우선순위·메모·결과 기록과 반응형 화면을 구현한다.
6. Gemini 구조화 분석·비교, 최근 결과 저장과 오래됨 판정을 구현한다.
7. 웹 알림함, 마감 강조, Resend 이메일, Vercel Cron을 연결한다.
8. 오류·빈 상태·접근성·보안·실데이터 품질을 검증한 뒤 Production 환경에 배포한다.

## 5. 테스트 및 완료 조건

- API fixture 계약 테스트로 온통청년 출처의 필수 필드 누락과 형식 변경을 감지한다.
- 정규화, 카테고리·지역 매핑, 날짜 해석, 중복 판정, 버전 해시를 단위 테스트한다.
- 동기화를 반복 실행해도 중복 정책이 생기지 않고 한 출처 실패 시 기존 정상 데이터가 유지되는지 검증한다.
- 익명 사용자는 공개 정책만 읽고, 로그인 사용자는 자신의 챙김·메모·AI 결과·알림만 접근할 수 있는지 RLS를 검증한다.
- 비회원 탐색 → 챙기기 → 로그인 → 원래 정책 저장 흐름을 E2E 테스트한다.
- 상태 전환, 우선순위, 메모, 결과 기록과 새로고침 후 유지 여부를 테스트한다.
- 1개 이상 정책 분석, 2~3개 정책 비교, 잘못된 개수, 타 사용자 정책 ID, Gemini 실패와 스키마 오류를 테스트한다.
- 마감 7일·1일 알림, 수신 거부, 상시 모집, 변경된 마감일, Cron 재실행 시 중복 방지를 테스트한다.
- 탈퇴 후 모든 사용자 소유 데이터와 인증 계정이 제거되는지 검증한다.
- 375px 모바일과 1440px 데스크톱에서 탐색·관리·비교가 모두 가능해야 한다.
- 키보드 탐색, 포커스 표시, 폼 레이블, 명도 대비와 오류 안내를 확인한다.
- 공식 신청 링크, 정책 출처, 최근 갱신 시각, AI 비확정 안내가 모든 관련 화면에 표시되어야 한다.

## 6. 확정된 전제와 제외 범위

- Supabase는 비어 있는 기존 프로젝트를 사용하고 전체 스키마를 새 마이그레이션으로 만든다.
- 온통청년 API 인증키는 이미 보유하고 있다.
- Vercel 프로젝트는 첫 커밋 후 생성하며 Preview와 Production 환경을 분리한다.
- 일정과 수익화 계획은 문서에 포함하지 않는다.
- 관리자 화면, 제품 행동 분석, 브라우저 푸시, 모바일 네이티브 앱, 서비스 내 신청, 상세 소득·가구 정보 수집은 MVP에서 제외한다.
